# Bug report

I started from the repository's behavior, wrote service and HTTP tests, then reproduced the problems below with requests against the unmodified app. The primary requested fix is pagination; the other fixes are small, test-backed extras. I kept the in-memory store, route shapes, and status vocabulary from `ASSIGNMENT.md`.

| Issue and location | Expected vs. observed before fix | Reproduction and change |
| --- | --- | --- |
| **Primary fix: pagination** - `task-api/src/services/taskService.js`, `getPaginated` | Page 1 should begin with item 1. With 3 tasks, `GET /tasks?page=1&limit=2` returned only task 3 because the offset was `page * limit`. | Create A, B, C; ask for page 1, limit 2. Unit and Supertest regression tests now check pages 1, 2, partial last, and out-of-range. Offset is `(page - 1) * limit`. |
| Partial status filter - `taskService.js`, `getByStatus` | Status should match one of `todo`, `in_progress`, `done` exactly. `?status=progress` returned `in_progress` tasks because `includes` used substring matching. | Create `in_progress` task, request `?status=progress`. Compare exact status now. Route rejects unknown status with 400; direct service lookup still yields `[]`. |
| Filters dropped pagination and accepted malformed query - `src/routes/tasks.js`, `GET /` | `?status=todo&page=1&limit=1` should contain one todo; it returned every todo due to an early return. `page=1oops` parsed as 1; zero silently fell back to 1. | Create two todos, query status plus limit. Apply filter then slice; reject zero, noninteger and unsafe integers with 400. For compatibility, unfiltered `GET /tasks` still returns an array (not a new response envelope). |
| Completion mutates unrelated priority and timestamp - `taskService.js`, `completeTask` | Completing should not change priority; doing it twice should retain the original completion time. High became medium, and second PATCH created another timestamp. | Create high priority, complete, advance fake clock and complete again. Preserve priority and reuse `completedAt` if already present. |
| General update overwrites identity and creates inconsistent completion - `taskService.js`, `update` | `id`, `createdAt`, `completedAt`, `assignee` should not be silently overwritten by a general update. Changing status to done should record completion; reopening should clear it. Existing spread copied arbitrary fields, so `PUT` changed an ID and left a done task with `completedAt: null`. | PUT a new ID and createdAt, then set status to done. Only editable fields are applied; completion timestamp follows status transitions. Existing status changes outside this route still use service logic. |
| Date validation said ISO, accepted human text - `src/utils/validators.js` | The contract says ISO 8601 timestamp. `January 1, 2000` was accepted since `Date.parse()` recognizes informal formats. | POST with that text and numeric zero, expect 400. Require a timestamp shape with timezone and a parseable date. This does not provide strict semantic round-trip validation for every calendar edge case; I would clarify accepted ISO variants before production. |

## Assignment/API ambiguities and remaining questions

- `README.md` calls the statuses `pending`, `in-progress`, `completed`; `ASSIGNMENT.md`, validators, stats, and implementation use `todo`, `in_progress`, `done`. Tests follow the assignment and code. The README should be aligned with the product contract, not guessed into a breaking status migration.
- `PUT` is called a "full update" in the README but the existing implementation performs a merge. I retained merge behavior rather than turn an unrelated bug fix into an API breaking change. Decide whether it should be PUT replacement or PATCH merge.
- The in-memory store is shared within one server and vanishes on restart/deploy; it has no authentication. A public deployment is a demo, not a production task tracker. Ask about persistence, user ownership, rate limiting, and error reporting before production.
